## Goal

Port `pure-reduce` to a current, exactly pinned REDUCE/CSL source revision and
provide a reproducible optional Windows package. Build the complete upstream
CSL system as the trusted generator, then ship only the verified runtime
closure required by the in-process Pure bridge.

The supported upstream baseline is the official REDUCE GitHub mirror commit
`7efba90661139ae9c73c99fddd55f3fb2fabf69a`. The mirror is generated from the
official SourceForge Subversion repository. The build must reject any source
tree whose commit or recorded source identity differs from this value.

## Decisions

- Build only 64-bit Windows REDUCE/CSL for the CLANG64 Pure distribution.
- Use MSYS2/CLANG64 as the reproducible build environment.
- Do not require MSYS2, a shell, compiler, or build tool at package runtime.
- Preserve the existing in-process `PROC_*` integration and public Pure API.
- Build the complete pinned upstream CSL source tree before selecting runtime
  artifacts; do not recreate the historical r2204 stripped source snapshot.
- Install the selected closure as the optional `PureReduce` component.
- Do not ship an image unless it was generated by the same pinned source and
  build whose bridge and runtime binaries are packaged with it.
- Do not make the full REDUCE command-line or graphical application part of
  `PureReduce`. It is outside the Pure bridge runtime contract.

## Build Architecture

The CMake build drives the official upstream build under MSYS2/CLANG64. It
performs these operations in order:

1. verify the checked-out REDUCE source identity against the pinned commit;
2. configure and build the complete 64-bit CSL implementation;
3. generate the matching REDUCE image and runtime data;
4. build the Pure bridge DLL against that exact CSL build;
5. run bridge tests against the complete build tree;
6. derive and audit the minimal runtime closure;
7. stage and validate the `PureReduce` component.

Network acquisition is allowed only in an explicit dependency-fetch step. A
normal rebuild consumes an already verified source tree or archive and does
not silently update it. The build records the source URL, commit, archive or
tree SHA-256, configure arguments, tool versions, elapsed build time, and full
and packaged sizes.

## Component Boundaries

### CMake orchestration

`pure-reduce/CMakeLists.txt` and focused modules below `pure-reduce/cmake`
own source verification, upstream configuration and build, bridge compilation,
runtime-closure collection, installation, and staged-package verification.
They do not encode symbolic-algebra behavior.

### Native bridge

The bridge is C++ because current `csl/cslbase/proc.h` places CSL declarations
in the `CSL_LISP` namespace and uses C++ signatures. It adapts current CSL to
the stable C symbols consumed by Pure, owns input/output callbacks, and
contains the small helper operations currently implemented by `proc-add.c`.

No C++ object, exception, allocator-owned buffer, or STL type crosses the
exported bridge boundary. Every exported entry point uses a C ABI. The bridge
catches C++ exceptions before returning to Pure and exposes a stable error
code plus diagnostic text. Returned strings have documented bridge-owned
lifetimes and are copied by the Pure layer where persistence is needed.

### Pure module

`pure-reduce/reduce.pure` retains the existing high-level symbolic API. It no
longer embeds `/usr/lib/pure`, relies on the working directory, or discovers
runtime files through an unrestricted `PATH`. It locates the installed module
directory through a bundle-relative loader contract and passes the image path
to CSL explicitly with `-i`.

### Runtime component

`PureReduce` contains only:

- `reduce.pure` and installed user-facing documentation;
- the bridge DLL;
- its matching REDUCE image and required runtime data;
- non-system DLLs in the audited PE import closure;
- pure-reduce and upstream REDUCE license/provenance material;
- a machine-readable inventory with path, purpose, origin, SHA-256, size, and
  applicable license for every installed file.

Headers, object files, compilers, build scripts, source checkout, and the full
REDUCE application are excluded from the runtime component. Source and
license obligations are satisfied through retained notices, an exact source
reference and fingerprint, and any redistributable source material required by
the applicable upstream terms.

## Initialization and Lifecycle

CSL initialization remains lazy and occurs on the first operation that needs
REDUCE. Initialization is transactional: failure to locate or load the DLL,
image, or runtime data leaves the module in an uninitialized state and reports
a diagnostic containing the failed stage and resolved path.

Only one CSL instance exists per Pure process. Repeated algebra operations use
that instance. `finish` is idempotent. Restart after `finish` is enabled only
if the pinned CSL passes the restart lifecycle test; otherwise the module
enters a deterministic finished state and later operations report that restart
is unsupported. The package must not advertise behavior that the pinned CSL
cannot pass repeatedly under test.

Input and output capture are reset on initialization failure and shutdown.
Bridge-owned buffers are released during shutdown, and callback pointers are
cleared before CSL state becomes unavailable.

## Error Handling

The bridge distinguishes loader, image, initialization, conversion, REDUCE
evaluation, and shutdown failures. It never lets a C++ exception unwind into
the Pure runtime. The Pure layer converts bridge failures into descriptive
Pure exceptions and preserves usability after recoverable REDUCE evaluation
errors.

Missing or mismatched packaged files fail closed. The loader does not search
MSYS2 or accept a same-named DLL from the current directory. Packaging fails
if dependency analysis finds an unresolved non-system import or a runtime file
outside the declared inventory.

## Validation

### Build-tree bridge tests

Tests against the complete upstream build cover:

- CSL initialization with an explicit image path;
- integers, big integers, floating-point values, strings, symbols, and lists;
- polynomial expansion and factorization;
- simplification of rational expressions;
- symbolic differentiation and integration;
- loading and using an optional REDUCE package;
- invalid input or evaluation failure followed by a successful calculation;
- input feeding and output capture.

Expected algebraic results are fixed in test data and compared structurally
where the Pure API returns expressions. Diagnostics are checked by stable
category rather than by fragile full upstream wording.

### Lifecycle tests

Lifecycle coverage includes lazy first start, repeated use of one instance,
multiple calls to `finish`, cleanup after failed initialization, and the
documented behavior of a call after `finish`. A restart stress test determines
whether restart is supported for the pinned baseline.

### Staged-package tests

Install `PureReduce` into a prefix whose path contains spaces. Run with
`PURELIB` unset, MSYS2 variables removed, and `PATH` restricted to the staged
Pure prefix and Windows system directories. Repeat the algebra and lifecycle
smoke tests, copy the prefix to a differently named location, and repeat them
again.

The package verifier compares the stage against the authoritative inventory,
walks the PE dependency closure, rejects undeclared or unresolved non-system
DLLs, checks every SHA-256, and confirms that no installed text or metadata
contains the original build or stage prefix.

### Installation lifecycle

Validation stages an initial installation, overlays the same version as an
upgrade, and removes only the files owned by `PureReduce`. It verifies after
each operation that unrelated Pure runtime files are unchanged. The final
clean Windows validation uses only explicitly staged artifacts.

## Metrics and Packaging Decision

CI records upstream fetch size, source size, full build-tree size, elapsed
build time, processor count, peak package stage size, final archive size, and
runtime file count. These measurements and the dependency inventory are added
to the TODO progress log.

`PureReduce` remains a separate optional installer component because it has an
independent large generated runtime, build pipeline, license inventory, and
validation lifecycle. TODO-49 may place its payload in a separately downloaded
artifact, but the component name, installed layout, and verifier contract
remain identical whether the bytes are embedded in or downloaded by the
installer.

## Failure Policy

If the pinned upstream commit needs small Windows or embedding corrections,
carry them as explicit, checksum-covered patches with upstream file and reason
recorded in the provenance manifest. Do not mutate the fetched tree
implicitly.

If current CSL cannot provide a complete image and in-process procedural
runtime on Windows, record the reproducible build failure and do not fall back
silently to r2204, an external REDUCE installation, or a subprocess protocol.
Changing integration architecture requires a new reviewed design.

If licensing or provenance cannot be established for every runtime artifact,
do not publish the component. If the runtime closure cannot be made independent
of MSYS2, the task remains open with the dependency evidence; no partial
runtime is shipped.

## Completion Criteria

TODO-47 is complete when:

- the pinned current REDUCE/CSL source builds reproducibly on Windows;
- the bridge preserves the supported existing Pure API against current CSL;
- the matching complete image and runtime closure pass all functional and
  lifecycle tests;
- the installed package relocates and runs with a sanitized environment;
- each installed file has recorded origin, SHA-256, size, and license;
- build time and full versus packaged size are recorded;
- installation, same-version upgrade, and removal pass independently;
- TODO-49 receives the stable `PureReduce` component and artifact contract.
